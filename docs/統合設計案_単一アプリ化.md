# 統合設計案｜3モジュールを1つのアプリにする

作成: 2026-07-26 / 対象: `english-grammar-trainer`

---

## 1. 現状の実像

「1つのサイト」に見えているが、実体は**独立した3つのSPAが同じドメインに並んでいるだけ**。

| | 基礎チェック | 英文法演習（ポラリス） | 英文解釈 |
|---|---|---|---|
| URL | `/grammar-knowledge-check/` | `/`（サイトルート） | `/reading/` |
| app.js | 645行 | 1601行 | 923行 |
| 連結 | `shared/flow-nav.js`（291行）が3つのlocalStorageを外から覗いて現在地を描画 | | |

`flow-nav.js` のコメント自身が制約を明記している —
「生徒識別が3モジュールで不一致という制約のため、v1 は『選択中の生徒基準で近似』する」。
**この"近似"を"正確"に変えることが、統合の本体。**

---

## 2. すでに共通化できている資産（作り直さない）

統合は「ゼロから」ではない。以下は既に揃っている。

1. **Supabase共通スキーマ** — `app_students`（全アプリ共用の生徒テーブル）＋ `app_progress(app, student_id)`。
   **サーバー側は既にマルチアプリ設計になっている。** 分断はクライアント側だけ。
2. **分野タクソノミ** — 基礎チェック16キー / ポラリス17キー（差は `preposition` のみ）。
   `foundation, pattern, verb_form, tense, modal, passive, infinitive, gerund, participle,
   comparison, relative, conjunction, subjunctive, nouns, adverb, negation`
   → 「基礎チェックの弱点分野 → ポラリスの該当問題」の橋渡しは**既に動いている**。
3. **デザイン言語** — 配色トークンがほぼ一致（`ink #141413` / `parchment #faf9f6` / `clay #b5532e` / `line` / `muted`）。
4. **harness** — `cloud.js` は2箇所でバイト単位で同一（md5一致）。

---

## 3. 分断されている点（統合作業の実体）

### 3-1. 生徒識別が3方式（最大の障壁）

| モジュール | 識別方式 | localStorageキー |
|---|---|---|
| ポラリス | 生徒**ID** ＋ ローカル名簿 ＋ 独自Supabase RPC（`?s=`＋token） | `polarisFinalGrammar1.progress.<studentId>` |
| 基礎チェック | **生徒の概念が無い**（端末に1つ） | `grammar-knowledge-check-v3` |
| 英文解釈 | 生徒**名（文字列）**をキーに含める | `polaris_reading_mvp_v1::<dataset>::<生徒名>` |

「同じ生徒の3モジュール分の進捗」を1つに束ねる手段が、現状クライアントには存在しない。

### 3-2. Supabaseのapp値が3つに分かれている

`english-practice` / `grammar-knowledge-check` / `eibun-kaishaku-polaris1`
→ 1人の学習者が3行に分散し、「この生徒の学習全体」を1レコードとして扱えない。

### 3-3. 重複インフラ

- `harness/`（cloud.js・engine.js・store.js）が2コピー
- `write-config.mjs` が2コピー（コメント以外は同一）
- ヘッダー／モジュールナビのマークアップが3コピー
- CSS変数を3ファイルが各自定義（状態色の名前が `green`/`ok`、`red`/`ng`/`danger`、`amber`/`warn` とバラバラ。英文解釈だけフォント変数を持たない）

### 3-4. ローカル開発環境では統合機能を検証できない

各アプリが別ポートで起動する構成のため、
- **別オリジン＝localStorageを共有しない**（モジュール間連携が原理的に再現できない）
- `shared/flow-nav.js` が **404**（実測確認済み。ルートが各アプリ配下のため `../shared/` が配信範囲外）

統合作業に着手する前に、ここを直さないと検証ができない。

---

## 4. 【要修正】統合以前に、現在動いていない機能がある

**基礎チェックの完了が、ポラリス側に一切伝わっていない。**

- 基礎チェックが書くキー: `grammar-knowledge-check-v3`
- `shared/flow-nav.js` と ポラリス `loadFoundationHistory()` が読むキー: `grammar-knowledge-check-v2`
- **移行処理は存在しない**（`grep` で確認済み）

ブラウザ実測での確認結果:

```
基礎チェックが書くキー v3        : 存在=true,  完了段階=5
flow-nav/ポラリスが読むキー v2   : 存在=false, 完了段階=0
基礎チェック自身のナビ           : 英文法演習=解放済み（v3を読むため正しい）
```

つまり本番で、5段階を完走した生徒に対しても
- 学習フローのステッパーが「基礎チェック 0/5・未着手」のまま
- ポラリスの英文法演習ゲートが**永久に解放されない**（`renderGrammarGate`）
- ポラリスの基礎学習ダッシュボードが常に空
- 弱点分野演習カードが常に非表示

統合の第一歩として、**まずこれを直す**（`v3` を読む＋`v2`があれば移行）。
統合を進めれば最終的にこのキー自体が消えるが、統合完了まで壊れたままにする理由はない。

---

## 5. 統合方針

### 採る案：単一シェル ＋ モジュール差し込み

```
/index.html            ← 唯一のHTML
/shared/
   identity.js         ← 生徒identity（唯一の正）
   store.js            ← 進捗ストア（唯一の正）
   shell.js            ← ヘッダー・ナビ・ステッパー・設定を1回だけ描画
   router.js           ← #/foundation, #/grammar, #/reading
   styles.css          ← デザイントークンの唯一の定義
/modules/
   foundation/         ← 出題・採点ロジックはそのまま移設
   grammar/
   reading/
```

**採らない案**
- *表面だけ統一（CSSとナビだけ揃える）* — 生徒識別と進捗が分断されたままなので「1つのアプリ」にならない。ステッパーは"近似"のまま。
- *フレームワーク導入で全面書き直し* — 3つとも素のJSの静的アプリ。教材データと採点ロジックを巻き込む書き直しはリスクだけ高い。

### 鉄則

**「土台の統一」と「各モジュールの中身の書き直し」を同じ工程に混ぜない。**
出題・採点・教材データには手を触れず、identity と store の付け替えだけを行う。
（AGENTS.md の Runaway Refactor / Kitchen Sink 回避）

## 6. 段階計画

### Phase 0 — 検証できる状態をつくる（前提工事）
- v2/v3 キー不整合の修正＋移行処理（§4）
- **リポジトリルートを配信する開発サーバー**を追加。本番と同じ配置・同一オリジンで動かす。
  → これが無いと以降の統合を一切検証できない。
- 完了条件: ローカルで3モジュールを行き来し、ステッパーが正しい段階数を出す。

### Phase 1 — 生徒identityの統一（統合の核）
- `shared/identity.js` を新設。生徒名簿・アクティブ生徒・共有セッション（`?s=`＋token）を集約。
  裏側は**既存の `app_students` をそのまま使う**（サーバー変更不要）。
- 基礎チェック: 生徒軸を獲得（現状は端末1つ）
- 英文解釈: 生徒**名**キー → 生徒**ID**キーへ
- ポラリスの独自RPC実装を identity.js へ引き上げ、harness と一本化
- 完了条件: どのモジュールで生徒を切り替えても、他の2つが即座に追随する。

### Phase 2 — 進捗ストアの統一
- `shared/store.js`：localStorage を `egt.progress.<studentId>` の1キーに集約し、
  中身を `{ foundation: {...}, grammar: {...}, reading: {...} }` の名前空間に。
- Supabase の app 値を `english-grammar-trainer` に一本化（1生徒＝1行）。
- 旧3キーからの移行を初回起動時に1回だけ実行。
- 完了条件: ステッパーが"近似"でなく実測値になる。ゲート判定が単一の情報源から出る。

### Phase 3 — シェルとデザインの統一
- `index.html` を1枚に。ヘッダー／モジュールナビ／ステッパー／設定メニューは `shell.js` が1回だけ描画。
- `shared/styles.css` にトークンを集約。
  先日の整列改修で基礎チェックに入れた `--gap-tight/group/section/band` を**正本のスケール**として採用し、
  状態色の名前を統一（`--ok` / `--ng` / `--warn` に寄せる）。
- 各モジュールは自分のビューCSSのみ保持し、トークンの再定義をやめる。
- 完了条件: 3画面のヘッダー・余白・状態色が単一定義から出ている。

### Phase 4 — 導線の統一
- ルーティングを `#/foundation` `#/grammar` `#/reading` に。
- **「つづきから始める」を1つに**：3モジュール横断で次にやるべき1手を決めて提示する
  （現状はポラリス内にだけ存在する）。統合の学習体験上の目玉になる部分。
- 旧URL（`/grammar-knowledge-check/`・`/reading/`）は**リダイレクトを残す**
  — 生徒に配布済みのQR・ブックマークを壊さないため。

### Phase 5 — 重複の廃棄
- harness 1コピー、`write-config.mjs` 1コピーへ。
- 各アプリのナビHTML・重複CSSを削除。
- `flow-nav.js` は shell に吸収して廃止。

## 7. 先に決めたいこと

| # | 論点 | 選択肢 | 補足 |
|---|---|---|---|
| 1 | 既存の学習進捗 | 自動移行 / リセット | 英文解釈は**生徒名（自由入力文字列）**がキーなので、IDへの機械的な対応付けは確実にはできない。ポラリスの `supabase_schema.sql` も前回移行時は「進捗リセット前提」と明記している。 |
| 2 | 配布済みURL | リダイレクト維持 / 切替周知 | QR・生徒共有URLを配布済みかどうかで変わる。 |
| 3 | Supabase の app 値 | 1つに統合 / 3つ維持 | 統合すると「1生徒＝1行」で扱えるが、既存3行のデータ移行が必要。 |
| 4 | 実施範囲 | Phase 0のみ先行 / 0-2まで / 全部 | Phase 0 は統合の是非に関わらず単独で価値がある（§4の不具合修正）。 |

---

## 8. 推奨する進め方

**Phase 0 を単独で先に実施する。**
理由: §4 の不具合は統合と無関係に現在の生徒に実害が出ており、かつ Phase 0 を終えない限り
Phase 1 以降の作業を検証する手段が無い（ローカルが別オリジン＋`shared/` が404）。

Phase 0 完了後に、上表の #1〜#3 を決めてから Phase 1 へ進む。
